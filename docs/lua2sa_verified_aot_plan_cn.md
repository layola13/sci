# 验证型 AOT Lua-to-SA 编译器（Tracked 路线）实施计划

> **设计日期**：2026年6月14日
> **核心目标**：设计一个编译器（`lua2sa`），将一个强类型的 Lua 语法子集直接编译为 **fully tracked、符合 Referee 静态安全验证的 SA 汇编**。
> **核心指标**：运行时零 GC 开销、100% 静态 Referee 通过、以及编译期自动确定并注入生存期管理（`!reg`）。

---

## 1. 核心理念：编译期模拟动态语义

为了真正体验 SA 的核心安全特性（仿射所有权、零垃圾回收开销、严苛的静态生存期校验），我们必须抛弃动态 VM 解释执行的模型。取而代之的是，利用**编译期静态分析**，将 Lua 语言结构直接翻译成 SA 的原生对应概念。

```
Lua 源码
   │
[类型推导引擎] ───────→ (推导出静态类型: i64, ptr, structs)
   │
[生存期与逃逸分析] ───→ (计算作用域，自动注入 stack_alloc 与 !reg)
   │
[单态化与代码发射] ───→ Tracked 安全 SA 代码 (.sa + .sal)
   │
[SA Referee 验证器] ──→ 静态验证的原生二进制 (零 GC, 100% 安全)
```

---

## 2. 映射表：将 Lua 语义静态翻译为 Tracked SA

| Lua 动态语义 | 静态 Tracked SA 翻译策略 |
|---|---|
| **动态变量** | **静态类型推导与单态化 (Monomorphization)**<br>所有变量在编译期推导为 SA 原生寄存器（如 `i64`、`f64`）。针对不同参数类型调用同一个函数的情况，在编译期复制出多个强类型 SA 函数体。 |
| **垃圾回收 (GC)** | **编译期生存期分析（线性/仿射类型）**<br>编译器分析变量在 AST 中的生命周期，自动在最后一个使用点后面注入 `!reg` 释放或 free 释放，从而彻底消灭运行时 GC 引擎。 |
| **动态 Key-Value 表** | **静态结构体布局 (Struct Layouts)**<br>拥有固定字段的表（如 `{x=1, y=2}`）在编译期被降低为 `.sal` 文件中的静态结构体定义。字段访问直接编译为 CPU 偏移量加载（如 `load t+8`）。 |
| **动态闭包** | **词法作用域逃逸分析**<br>如果闭包的生命周期不逃逸出当前函数（不被 return，也不存入全局表），则直接在栈上进行分配。逃逸闭包将被禁止，或编译为强所有权的引用计数容器。 |

## 3. 翻译实例：Lua 源码 $\rightarrow$ Fully Tracked 静态 SA

下面展示一个标准的 Lua 片段如何通过该路线翻译为零 GC 开销、完全受静态所有权验证保护的 SA 代码。

### Lua 源码 (`math_test.lua`)
```lua
local function multiply(t, factor)
    return t.val * factor
end

local item = { val = 42 }
local result = multiply(item, 2)
return result
```

### 编译生成的 Tracked SA 汇编

首先，编译器为表结构静态生成一个布局文件：
```sal
// math_test.sal - 自动生成的结构体布局
#struct ItemLayout {
    val: i64
}
```

然后，编译器生成完全符合所有权追踪的 `.sa` 代码：
```sa
// math_test.sa - 自动生成的 Tracked 汇编
@import "math_test.sal"

@multiply(t: ptr, factor: i64) -> i64:
L_ENTRY:
    // 字段读取受 math_test.sal 布局的安全保护与边界校验
    val = load t+0 as i64
    res = mul val, factor
    !t // 明确消费并回收 t 的所有权
    return res

@export main() -> i64:
L_ENTRY:
    // 在栈上直接分配结构体空间（没有堆分配，没有 GC 压力！）
    item = stack_alloc 8
    store item+0, 42 as i64
    
    // 调用强类型函数，传递被静态跟踪的 item 指针
    result = call @multiply(item, 2)
    
    // 编译器能够静态确保 item 的所有权已被 multiply 消费并妥善清理。
    // 如果之后再次访问 item，SA 编译器会直接报错拒签。
    return result
```

### 为什么该方案能完美展现 SA 的价值：
1.  **零运行时 GC**：数据通过 `stack_alloc` 栈分配，生存期完全绑定于栈帧。
2.  **显式所有权管理**：`item` 指针在传参时发生所有权转移，并在最后一个出口被精确销毁。如果开发者在代码中产生内存泄露，SA 编译器在编译期就会报错。
3.  **极速执行**：全部为原生 CPU 指令（`i64` 加减乘除），没有联合体动态拆箱和元表慢速分派。

## 4. 四阶段具体实施计划

### 阶段 1：渐进式类型推导引擎（第 1–3 周）
1.  使用 Python 或 Rust 编写解析器，支持带可选类型标注的 Lua 变体语法（渐进式类型，如 `local x: integer = 1`）。
2.  实现 Hindley-Milner 类型推导算法，对未标注的变量和函数参数进行全局类型推断。
3.  对于无法在编译期推断出确定静态类型的 Lua 脚本（如动态改变类型的变量、混合类型的非同构数组），直接报错拒绝编译。

### 阶段 2：编译期生存期与逃逸分析器（第 4–6 周）
1.  为输入的 Lua 代码构建控制流图（CFG）。
2.  进行**活跃变量分析（Live Variable Analysis）**，精确定位每个表或字符串最后一次被访问的语句。
3.  在最后一次访问点后，自动注入 `!ptr` 或内存释放接口调用。
4.  进行**逃逸分析（Escape Analysis）**：对于不逃逸出当前函数作用域的表，将其由堆分配降级为 SA 栈分配（`stack_alloc`），进一步榨干性能。

### 阶段 3：表到结构体布局映射器（第 7–9 周）
1.  分析表的初始化语句。对于具有固定 Key 的表（如 `{x=1, y=2}`），在编译生成的 `.sal` 布局文件中将其转化为对应的 C 风格结构体定义。
2.  将所有属性访问（如 `t.x`）转化为基于静态内存偏移量的直接 load/store。
3.  限制或直接拒绝动态 Key 寻址（如 `t[var]`），除非 `var` 是一个编译期常量。

### 阶段 4：单态化与代码发射后端（第 10–12 周）
1.  实现单态化机制：如果泛型函数被不同类型的参数调用，自动在 SA 中复制出两份强类型函数（如 `add_i64` 和 `add_f64`）。
2.  发射最终的 Tracked `.sa` 安全汇编。
3.  接入 `sci` 编译器，利用 SA 的 Referee 静态验证器对生成的代码进行安全扫视，证明其具有数学级的内存安全且无任何内存泄漏。

## 5. 语言限制（此编译器能够接受的 Lua 子集）

为了使编译期静态安全校验可行，此路线下的 `lua2sa` 必须对 Lua 语言做如下强约束限制：
1.  **静态类型约束**：运行时变量不能动态改变类型。
2.  **禁止混合类型的 Table**：表的行为必须像 C 结构体或单类型的同构数组。
3.  **禁止动态代码执行**：不支持 `load` 和 `loadstring`。
4.  **禁止任意循环引用**：在编译期检测循环引用并拒绝，除非使用明确声明的弱引用容器。
