# 为什么直接进行 Lua 到 SA 的编译不可行：底层技术深度评估

> **评估日期**：2026年6月14日
> **评估主题**：Lua 运行时语义与 SA (Safe ASM) 静态验证模型之间的底层冲突
> **目标**：从类型系统、内存管理、闭包作用域、指令膨胀和动态执行五个维度，深入剖析为什么我们无法开发一个直接将 Lua 源码 AOT 编译成 Tracked 级别原生 SA 代码的编译器。

---

## 1. 类型断层：动态装箱 vs. 静态 Referee 验证

Lua 是**动态类型语言**，变量本身没有类型约束，只有运行时的值有类型。而 SA 是**静态验证的汇编语言**，每一个寄存器在编译期都必须具有确定的静态类型（如 `i64`、`ptr` 等），以供 Referee 进行线性安全校验。

### 动态分派（Dynamic Dispatch）难题
在 Lua 中，最简单的加法 `x = a + b` 具有极高的多态性。在运行时，操作数可能是整数、浮点数、需要隐式转换的字符串，或者是绑定了 `__add` 元方法的表。

如果我们直接将其编译为 SA 汇编：
1. SA 无法直接生成 `t = add a, b` 这样的 CPU 指令，因为在编译期根本不知道 `a` 和 `b` 的具体类型。
2. 编译器必须将每一个 Lua 变量在 SA 中表示为一个庞大的装箱联合体（Boxed Union），即 `LuaTValue` 结构指针。
3. 对应的直接 SA 代码生成不得不变成极其繁琐的类型分派逻辑：
   ```sa
   // 在 SA 中模拟动态类型检查与多分派
   a_tag = load a+0 as u64
   b_tag = load b+0 as u64
   is_int_a = eq a_tag, LUA_TINTEGER
   is_int_b = eq b_tag, LUA_TINTEGER
   both_int = and is_int_a, is_int_b
   br both_int -> L_FAST_ADD, L_SLOW_DISPATCH
   
   L_FAST_ADD:
       a_val = load a+8 as u64
       b_val = load b+8 as u64
       res_val = add a_val, b_val
       store x+0, LUA_TINTEGER as u64
       store x+8, res_val as u64
       jmp L_DONE
       
   L_SLOW_DISPATCH:
       // 调用手写 C 风格的运行时 helper 来查找元表、处理浮点数或字符串转换
       call @lua_runtime_add_fallback(&a, &b, &x)
       jmp L_DONE
   ```
4. **结论**：直接直译并没有生成“原生 SA 指令”，而是将简单的 Lua 逻辑变成了无数的指针 load/store 以及慢速的 runtime 接口调用。这无异于在汇编中“手写解释器”，直接扼杀了性能。

---

## 2. 内存断层：垃圾回收 (GC) vs. 仿射所有权 (Affine Ownership)

这是最本质的物理限制。
*   **Lua** 内存生命周期由 **垃圾回收器 (GC)** 主导。对象（表、闭包、字符串）之间可以有任意的共享引用，甚至可以形成循环引用（例如 `t.self = t`）。
*   **SA** 强制推行严格的 **仿射所有权（Affine Ownership）**。任何分配的资源在任一时刻只能有唯一的所有者。一旦被赋值给新变量或传入函数，其所有权立即被消费（`^` / `Consumed`）。除非完全退化为 FFI `Untracked` 的不安全指针模式，否则 SA 不允许任何形式的循环和多路共享。

### 变量跟踪链的崩溃
如果我们将 Lua 表的创建直译为受 SA 跟踪的安全所有权代码：
```lua
local t = {}
t.self = t  -- 循环引用
return t
```
在 Tracked SA 模式下，这是根本无法通过静态校验的：
1. 如果 `t` 是受所有权保护的 SA 指针，执行 `t.self = t` 会触发 Move 违规。写入字段会消费 `t` 本身，导致在后续的外层作用域中无法再次引用 `t`。
2. 即使没有循环引用，由于引用关系可以在运行时任意共享（例如存入全局表），SA 无法在静态编译期计算出某个表究竟在何时需要被释放（`!`）。
3. **唯一的妥协方案**：生成的 SA 必须抛弃 Referee 校验，将所有指针标记为 `Untracked`（不安全模式），并在 SA 侧实现一个垃圾回收器运行时。但这直接导致 SA 静态所有权校验的物理价值荡然无存。

## 3. 作用域断层：Lua Upvalues vs. SA 栈物理隔离

Lua 支持闭包，内部函数可以读取并修改外部函数的局部变量（即 Upvalue）。当闭包的生存期超越其外层函数时，被捕获的变量会自动从栈“逃逸”到堆内存中（变成 Closed Upvalue）。

```lua
function create_counter()
    local count = 0
    return function()
        count = count + 1
        return count
    end
end
```

### SA 的栈隔离与别名冲突
1. SA 强制推行严格的栈隔离。子函数完全无法跨调用栈边界读写父函数的局部变量寄存器。
2. SA 仿射模型下，两个函数不能在没有违反 Referee Aliasing 规则（即同一时间只能有一个活跃的可变引用）的前提下，可变地共享同一个堆内存指针。
3. 为了编译闭包，直译器必须完全模拟 Lua 复杂的 `UpVal` 结构：
   *   所有**可能被闭包捕获的局部变量**，从声明伊始就必须放弃栈寄存器分配，转而在堆上分配一个共享盒子（`UpVal` 结构体）。
   *   对 `count` 的每次读写都必须编译成双重间接寻址（先 load upvalue 指针，再 load 具体值）。
4. 这种堆模拟效率低下，且会导致生成的 SA 代码充斥着繁杂的寻址细节，LLVM 后端极难对其进行寄存器优化。

---

## 4. 指令膨胀：缺乏 Switch/Match 与手动清理的代偿

在低级 SA 汇编中，由于没有 `switch` 结构且每个分支必须在退出前显式销毁所有不再使用的活跃变量（`!reg`），直译 Lua 的控制流会导致生成的汇编文件体积爆炸式增长。

例如，下面一行 Lua 代码：
```lua
obj.width = width + 10
```
在直接转译时，必须生成对应的 SA 指令包括：
*   检查 `obj` 是否为表（条件跳转）。
*   检查 `width` 是否为数字（条件跳转）。
*   解析 metatable 分支。
*   在每一个跳转路径的分支出口手动释放所有的临时寄存器所有权（`!obj`、`!width` 等）。

这一行 Lua 代码将产生 **50 到 100 行的 SA 代码**。一个 1,000 行的普通 Lua 脚本会转译出 **50,000 行以上的庞大 SA 汇编**：
*   这会极大增加 SA 编译器 `sci` 的 Flattener 和 Referee 分析阶段的内存占用，甚至导致编译超时。
*   由于每一条退出路径都复制了大量的 `!reg` 清理指令，编译出的原生二进制体积会急剧膨胀。

---

## 5. 动态执行屏障 (Dynamic load)

Lua 的核心特性之一是支持动态加载并执行字符串代码：
```lua
local f = load("return " .. arg[1])
print(f())
```
如果 `lua2sa` 想要支持 `load`：
1. 编译出来的原生二进制文件中，必须内置一个完整的 Lua-to-SA 编译器前端。
2. 此外，二进制中还必须携带完整的 `sci` 编译器本身（Zig 编写且依赖 LLVM）。
3. 这在物理上是完全不可取的。因此，直接转译为 SA 必然面临动态加载特性的彻底丧失，除非回退到当前的 VM 解释执行模式。

---

## 总结

直接直译 Lua 为安全 Tracked SA 存在根本性的**抗阻失配（Impedance Mismatch）**。它试图将一门动态、强 GC 依赖的脚本语言，硬塞进一个底层、静态验证且基于单所有权的仿射汇编语言中。

如果我们一定要使用 SA，我们**不应该去编译通用 Lua 源码**。正确的战略路线是：
*   **路线 A**：使用 `bc2sa`，将官方 C-Lua 解释器整体同化并编译为不安全的 `Untracked` 模式，SA 只做最外层的 FFI 气闸舱 syscall 拦截。
*   **路线 B**：直接新建一门与 SA 物理特性完全契合的、安全的线性 AST 语言（如 **Sla**），在编译期把所有类型、生存期和释放动作彻底收敛。
